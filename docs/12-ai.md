# STUDY-alg.md — `fs/alg/libalgo.so` Static Analysis (offline)

Produced entirely offline from local copies of `fs/alg/libalgo.so` (5,743,920 bytes,
sha1 `<redacted-hex>`) and `fs/app/bin/media` (348,116 bytes,
sha1 `<redacted-hex>`), both 32-bit little-endian ARM/EABI5
(`libalgo.so` is `ET_DYN`, PIC, Thumb-2 code; `media` is `ET_EXEC`, non-PIE, Thumb-2 code).
`libalgo.so`'s `.symtab` is **not stripped** (full local+global symbol table, 41,624 entries),
which is what made deep reconstruction possible without a decompiler. Tools: `pyelftools`
(`.dynsym`/`.symtab`/relocations), `capstone` (ARM/Thumb-2 disassembly), `cxxfilt` (Itanium
C++ demangling). All addresses below are link-time virtual addresses inside `libalgo.so`
unless marked `[media]`.

---

## 1. API surface — what `media` actually calls

`media` never links `libalgo.so` at load time (`readelf`-level cross-reference of `media`'s
269 undefined dynamic symbols against `libalgo.so`'s 674 defined ones: **zero overlap**).
Everything crosses the boundary through `dlopen("/alg/libalgo.so")` + `dlsym()`, confirmed by
literal strings in `media`: `dlsym`, `dlopen`, `libalgo_handle`, `/alg/libalgo.so`,
`algo_process_init dlopen %s Error: %s`, `algo_process_init dlsym %s error: %s` (file offsets
`0x31c68` region).

`libalgo.so` exports exactly **16** `extern "C"` (non-mangled) global functions plus a
statically-linked copy of libwebp (`WebP*`) and a small WAV reader (`wav_*`, dead code — no
audio path in this library). All 16 are present verbatim as strings inside `media`, confirming
every one is dlsym-resolved and used:

| Symbol (link addr) | Size | Signature (from calling-convention evidence) | Role |
|---|---|---|---|
| `petkit_algo_init` | 0x4b3ac / 272 | `(...)→int` | Load `/alg/alg_model.txt`, construct + init the per-stage C++ objects (body/face/feat/food/skeleton/behavior/classify), each of which calls `AX_ENGINE_*` itself (§5) |
| `petkit_algo_deinit` | 0x487b4 / 444 | `()→void` | Tear down all stage objects |
| `petkit_algo_frame_input` | 0x47a2c / 604 | `(frame,…)` | Feed one video frame into the pipeline |
| `petkit_algo_detect_run` | 0x49654 / 3656 | large | Core per-frame detect/track/behavior driver |
| `petkit_algo_food_detect_run` | 0x47de8 / 104 | | Runs the food-segmentation model path only |
| `petkit_modify_algo_threshold` | 0x47f24 / 72 | `(float bodyThresh, float faceThresh, float keypointThresh, float featThresh, float bodyMoveRatio, float bodyPlateThresh)` | **Confirmed by disassembly** (§2) — 6 VFP float args `s0..s5`, one write each to 3 singleton class instances |
| `petkit_modify_discern_total_score` | 0x47f6c / 28 | `(float)` | Sets a global re-ID acceptance-score gate |
| `petkit_set_tracker_interval` | 0x47ea4 / 24 | `(int)` | SORT tracker cadence |
| `petkit_set_algo_day_night_mode` | 0x480e8 / 4 | `(int)` | IR/day-night flag, trivial stub |

| `petkit_clear_feature` | 0x47e50 / 24 | thin wrapper | Wipe gallery — see §3 |
| `petkit_set_event_start_signal` | 0x47ec4 / 36 | thin wrapper → `CPetkitAlgoPetfeat::petkit_set_event_start(unsigned long long)` | Arm one result slot for an event id |
| `petkit_get_event_result_info` | 0x47ee8 / 36 | thin wrapper → `CPetkitAlgoPetfeat::petkit_get_event_result(unsigned long long, void(*)(int, petkit_event_result_info*))` | Poll/callback result fetch — §4 |

**Disassembly evidence** for the two thin-wrapper patterns (`petkit_get_event_result_info` @
`0x47ee8`, and identically `petkit_set_event_start_signal` @ `0x47ec4`): both load a global
singleton pointer through a GOT-relative access (`ldr r4,[pc,#N]; add r3,pc; ldr r4,[r3,r4];
ldr r0,[r4]`), then `blx` into a local PLT stub that resolves (per `-fPIC` self-call
convention) to the matching mangled `CPetkitAlgoPetfeat::` member function. This proves the
public C API is a **1:1 pass-through** to one global `CPetkitAlgoPetfeat` instance's methods —
no extra logic, no rate limiting, no filtering added at the C boundary.

## 2. Threshold wiring — `petkit_modify_algo_threshold` (exact field offsets, hard evidence)

Full Thumb-2 disassembly at `0x47f24` (72 bytes):

```
ldr r3,[pc,#0x34]; ldr r2,[pc,#0x34]; add r3,pc     ; r3 = GOT base
ldr r4,[pc,#0x34]; ldr r1,[pc,#0x34]
ldr r2,[r3,r2]; ldr r2,[r2]                          ; r2 = *g_petbody   (singleton #1)
vstr s0,[r2,#0x1c]                                   ; bodyThresh    -> petbody+0x1c
ldr r4,[r3,r4]; ldr r4,[r4]                          ; r4 = *g_petface  (singleton #2)
vstr s1,[r4,#0x1c]                                   ; faceThresh    -> petface+0x1c
vstr s2,[r4,#0x20]                                   ; keypointThresh-> petface+0x20
ldr r3,[r3,r1]; ldr r3,[r3]                          ; r3 = *g_petfeat  (singleton #3)
vstr s3,[r3,#0x1c]                                   ; featThresh    -> petfeat+0x1c
vstr s4,[r2,#0x20]                                   ; bodyMoveRatio -> petbody+0x20
vstr s5,[r2,#0x24]                                   ; bodyPlateThresh -> petbody+0x24
bx lr
```

Six 32-bit float args arrive in VFP registers `s0..s5` (AAPCS-VFP hardfloat calling
convention) in **exactly the order named in the assignment** — `bodyThresh, faceThresh,
keypointThresh, featThresh, bodyMoveRatio, bodyPlateThresh` — and are written to three
distinct global singleton C++ objects (`CPetkitAlgoPetbody`, `CPetkitAlgoPetface`,
`CPetkitAlgoPetfeat`, all instantiated once by `petkit_algo_init`). This corroborates the
offset `+0x1c` independently seen inside `CPetkitAlgoPetfeat::petkit_petfeat_process` (`vldr
s14,[r0,#0x1c]` at `0x59ba4`, i.e. the feat object reading back its own `featThresh`).

## 3. Embeddings — dimension, gallery storage, retrievability

### 3.1 Embedding dimension: **512 × float32, confirmed from the model itself**

`fs/alg/petkit_face_rec_mtl_s2_v5_sim.axmodel` (Pulsar2 4.1, commit `2497d324`) embeds its own
JSON-ish output-tensor metadata in the container header:

```
outputs_info: {"feat": ["FP32", [1, 512]], "prob": ["FP32", [1]]}
```

So the model emits two tensors per inference: a **512-float (2048-byte) `feat` embedding**
and a scalar `prob` (almost certainly a face-quality/liveness gate consumed alongside
`featThresh`, not part of the identity vector). This is direct ground truth from the
compiled model container, not inferred from code. For context, the same technique run
against the other six `.axmodel` files confirms the whole pipeline's tensor shapes:

| Model (manifest key) | Output tensors |
|---|---|
| `body_model` (`petkit_pet_1class_2026_04_15`) | `output: [1, 5100, 33]` — NanoDet-style anchor grid (matches `CPetkitAlgoPetbody::petkit_body_parse_nanodet_output(_AX_ENGINE_IO_T*)`, `petkit_petbody_decode_box`) |
| `face_model` (`petkit_cat_dog_mv2_035_kps_porb_roi_v8_224x224`) | `output0:[1,2058,4]` (bbox), `output1:[1,2058,2]` (cat/dog), `output2:[1,2058,10]` (5 keypoints×2), `output3:[1,2058,3]` (prob/roi) — matches the filename `kps_porb_roi` |
| `feat_model` (`petkit_face_rec_mtl_s2_v5_sim`) | `feat:[1,512]`, `prob:[1]` — **the re-ID embedding** |
| `skeleton_model` (`petkit_mobilepose_v1.3`) | `output:[1,21,2]` — 21 pose keypoints |
| `behavior_model` (`petkit_pets_behavior_rec_0601_v1.3`) | `onnx::Gemm_1596:[1,512]` (an unrelated 512-d intermediate feature, NOT the re-ID embedding — different model, different purpose) + `output:[1,2]` |
| `food_model` (`petkit_pp_fooddet_...`) | `seg_logits:[1,3,128,416]`, `reg:[1,1]` |
| `classify_model_bb` (`tsn_v17_bb`) | `fetch_name_0:[1,1280]` — MobileNetV2-width backbone feature feeding `classify_model_hd` |

(Face-crop model **input** resolution was not recoverable from the container metadata window
inspected — flagged as an open question in §8, do not assume 112×112.)

### 3.2 Where the embedding lives internally — retrievable in-process, not via the public API

`CPetkitAlgoPetfeat::petkit_petfeat_process(std::vector<float>&, std::vector<BoxInfo>&)` and,
more importantly, the uniform per-stage driver present on **every** detector class —
`CPetkitAlgoPetbody::petkit_algo_model_run`, `CPetkitAlgoPetface::petkit_algo_model_run`,
`CPetkitAlgoPetfeat`'s equivalent — all share this exact signature (demangled):

```
petkit_algo_model_run(unsigned char* frame, int w, int h,
                       void(*cb)(int, BoxInfo*, unsigned long long),
                       std::vector<std::vector<float>>& outFeatures,
                       std::vector<std::pair<std::vector<float>, std::vector<unsigned char>>>& outFeatureCropPairs)
```

`outFeatures` is a **per-detection list of raw float vectors** and `outFeatureCropPairs` pairs
each feature vector with its raw crop bytes. These are ordinary exported (global-bind, not
hidden-visibility) C++ symbols in `libalgo.so`'s dynamic symbol table — so the raw 512-d
embedding for a given detection genuinely exists as a concrete `std::vector<float>` at
runtime, and the symbol is technically dlsym-reachable by name. **However**: none of these
mangled C++ methods are among the 16 symbols `media` actually calls (§1) — the public,
documented-by-usage API surface stops at `petkit_get_event_result_info`, whose struct (§4)
carries only `event_pet_id` + `pet_score`, no raw vector. Calling the mangled methods directly
from a second process would require (a) constructing a binary-compatible `CPetkitAlgoPetfeat`
C++ object (private layout, not header-available), and (b) matching the exact AAPCS
struct-by-invisible-reference ABI for the three `std::vector`/`std::pair` out-params — fragile,
undocumented, and liable to break silently on any Petkit firmware update. **Verdict: not
practically retrievable through any exported function without reverse-engineering a private
class layout; recommend re-running the same `.axmodel` independently instead (§7).**

### 3.3 Gallery storage — `/opt/feature.bin`, confirmed by adjacent debug strings

Contiguous rodata block at file offset `0x33ff00–0x340370` (function-local string pool for the
`CPetkitAlgoPetfeat` class, symbol `18CPetkitAlgoPetfeat` sits right after it) contains, in
order:

```
"feature pet id: %u"                                  (0x34009c)
"feature pet face_feature_id: %u"                      (0x3400b0)
"The %s is not exists!!!"                              (0x3400d8)
"extract_feature_from_file error reading crc"          (0x3400f4)
"Error reading from file or file is corrupted."        (0x340120)
"Face feature crc is not same!!!"                      (0x340150)
"v0.0.3"                                                (0x340170)
"The alg version is not compared!!!"                    (0x340178)
"/opt/feature.bin"                                      (0x3401a0)
"fsync failed"                                          (0x3401b4)
```

This is unambiguous: the enrolled-pet gallery is a **single versioned binary file,
`/opt/feature.bin`**, with a CRC32 check and a `"v0.0.3"` format-version tag, written with
`fsync()`. It is loaded/parsed by `CPetkitAlgoPetfeat::petkit_extract_feature_from_file()`
(mangled symbol `_ZN18CPetkitAlgoPetfeat32petkit_extract_feature_from_fileEv`, `0x54afc`,
1016 bytes) and (inference, function name) written by
`CPetkitAlgoPetfeat::petkit_face_feature_save_face_feature()` (`0x53a44`, 140 bytes). Entries
are keyed by the pair `(pet_id, face_feature_id)` — matches the public
`petkit_feature_add(unsigned int pet_id, unsigned int face_feature_id, char* path)` /
`petkit_feature_del(unsigned int, unsigned int)` signatures exactly (mangled:
`_ZN18CPetkitAlgoPetfeat18petkit_feature_addEjjPc`). `/opt/feature.bin` is **not present** in
either the static `alg.img` extraction or the offline backup image (it is populated at
runtime under the writable `/opt` UBI volume, outside what we have offline) — its exact byte
layout (header/CRC/record size) was not recoverable without a live copy; flagged as an open
question (§8).

### 3.4 Gallery population path — local file, not a live URL fetch

`petkit_from_url_detect_feature(char*)` — despite the name — cannot itself perform HTTP:
`libalgo.so` imports **zero** networking symbols (`curl`, `http`, `sock*`, `ssl*`, `connect`
all absent from its 346 undefined dynamic symbols). Per `STUDY.md`'s architecture map, only
`ctrl`/`cloud` have HTTP clients. **Inference**: the char* argument is a local path to an
already-downloaded photo (fetched by `cloud`'s `/dev_discern_config`-style endpoint and hand
- off via the mqueue bus or a shared tmp path to `media`, which then calls into libalgo), i.e.
enrollment from the phone app is: cloud downloads photo → local file → `media` dlsym-calls
`petkit_feature_add`/`petkit_from_url_detect_feature` with the **local path** → libalgo runs
`feat_model` on it → appends to `/opt/feature.bin`.

## 4. Result struct — `petkit_event_result_info` (field order from a printf format string, exact layout not disassembled)

`media`'s own debug format string (file offset `0x33ee2` in `media`, referenced from the
`petkit_event_result_callback` @ `media:0x1cc58`, size 172) prints one entry as:

```
"the %d's petid: %u, score: %f, action_type: %d, exception_type: %d, event_pet_id: %u"
```

giving the field **order and C types** for one per-pet result record: `index (int)`,
`pet_id (uint32)`, `score (float)`, `action_type (int32)`, `exception_type (int32)`,
`event_pet_id (uint32)`. `libalgo.so`'s own internal debug-print rodata block (adjacent to the
`CPetkitAlgoPetface`/`CPetkitAlgoPetfeat` string pools, `0x33ffcc–0x340048`) has a
superset/related set of labels in this order: `pet_score`, `action_type`, `exception_type`,
`event_pet_id`, `start_time`, `end_time`, `exception_start_time` — the three extra `*_time`
fields (`unsigned long long`, printed with `%llu` given the adjoining format specifiers)
belong to the exception/event timing portion of the struct, separate from the per-pet score
record. Attempting to recover exact byte offsets inside `media`'s
`petkit_event_result_callback` produced a misaligned Thumb decode (the function does not begin
with the expected `push`/`sub sp` prologue at its own `.symtab` value, and chasing the
alignment further was not a productive use of remaining time) — **field order and types above
are solid (verbatim printf format string), exact byte offsets/`sizeof` are not** and should be
treated as an open question, resolved fastest with a single `gdb`/`strace` read of the struct
live rather than more static disassembly.

**No raw feature vector, embedding, or bbox field appears in this printf** — the public result
struct is limited to identity (`pet_id`/`event_pet_id`), a scalar `score`, and
action/exception/timing metadata. This corroborates §3.2: the embedding does not cross the
public API boundary.

## 5. Crops — `/tmp/saveFace.jpg`, shell-script upload hand-off

Same rodata block (`0x340050–0x34009c`) additionally contains:

```
"/opt/upload_face"                          (0x340050)
"/tmp/saveFace.jpg"                          (0x340064)
"sh /opt/upload_face_jpg %d %d %d"           (0x340078)
```

So `libalgo.so` writes the enrolled/matched face crop to **`/tmp/saveFace.jpg`**, then invokes
a shell script `/opt/upload_face_jpg` with **three integer arguments** (inference from
adjacent `feature pet id: %u` / `feature pet face_feature_id: %u` strings and the
`petkit_feature_add(pet_id, face_feature_id, path)` signature: almost certainly
`pet_id face_feature_id <score-or-event-id>`) — this is the local→cloud upload path for a
newly-enrolled or newly-observed face, handled entirely outside `media`'s own process (a
`system()`/`popen()`-style shell-out, not a further dlsym call).

`CPetkitAlgoPetface::petkit_algo_face_pre_process(std::vector<float>&, FaceCropBBoxInfo&,
std::vector<unsigned char>&)` (`0x4e680`, 1060 bytes) is the actual crop generator: it takes a
named `FaceCropBBoxInfo&` structure (bbox is a first-class, named type internally — not just
raw floats) and produces both a normalized float tensor (model input) and raw crop bytes
(`vector<unsigned char>&`, presumably the JPEG-encoded or raw RGB crop later passed to
`WebP*`/`cv::imwrite`-style code for `/tmp/saveFace.jpg`). `media`'s own string table separately
references `/tmp/fPre_pet.jpeg` and the bus handler `dispatch_handler_recv_pet_face_pic_info` —
these belong to `media`'s own ISP preview-snapshot mechanism (§10 of `STUDY-app.md`), a
**different, lower-resolution artifact** from the algo's own `/tmp/saveFace.jpg`; do not
conflate the two. Crop resolution was not pinned down (the `.axmodel` container inspection did
not surface an explicit `feat_model` input shape) — open question, §8.

**Bbox availability for our own cropping**: `FaceCropBBoxInfo` exists as a named struct
threaded through `petkit_algo_face_pre_process` and `petkit_face_generatebbox2`, and every
`algo_model_run` variant's `void(*cb)(int, BoxInfo*, unsigned long long)` callback parameter
delivers a `BoxInfo*` per detection at C++ call time — but, same as §3.2, this callback is
internal to the C++ call graph, not one of the 16 dlsym-exposed C functions. **We cannot get a
bbox from the public API either** — only `pet_id`/`score`/timing via
`petkit_get_event_result_info`. A first-party agent wanting a bbox must detect the pet/face
itself (e.g. reusing `body_model`/`face_model` on frames pulled from the media ring) rather
than reading one out of libalgo.

## 6. NPU / AX Engine usage

### 6.1 API family: exclusively `AX_ENGINE_*`, no `AX_JOINT_*`

`libalgo.so`'s 346 undefined (imported) dynamic symbols include exactly these Axera-prefixed
entries:

```
AX_ENGINE_CreateContext   AX_ENGINE_CreateHandle   AX_ENGINE_Deinit
AX_ENGINE_DestroyHandle   AX_ENGINE_GetIOInfo       AX_ENGINE_Init
AX_ENGINE_RunSync
AX_IVPS_CropResizeV2Vpp   AX_IVPS_CropResizeVpp     AX_IVPS_CscTdp   AX_IVPS_Dewarp
AX_POOL_GetBlock          AX_POOL_GetBlockVirAddr   AX_POOL_Handle2PhysAddr
AX_SYS_MemAlloc           AX_SYS_MemAllocCached     AX_SYS_MemFree
```

No `AX_JOINT_*` symbol appears anywhere. `_AX_ENGINE_IO_T*` and `_AX_ENGINE_IO_INFO_T*` are
used directly as C++ parameter types in demangled signatures (e.g.
`CPetkitAlgoPetface::petkit_face_generatebbox2(_AX_ENGINE_IO_T*, ...)`,
`CPetkitAlgoPetbody::petkit_petbody_process(_AX_ENGINE_IO_INFO_T*, _AX_ENGINE_IO_T*, ...)`) —
i.e. the code queries tensor shapes/addresses via `AX_ENGINE_GetIOInfo` at runtime rather than
hardcoding them, consistent with §3.1's inability to find a compile-time embedding-dimension
constant inside `libalgo.so` itself (the true dimension only exists in the `.axmodel`
container).

### 6.2 Who calls `AX_ENGINE_Init` — **`libalgo.so` does, `media` does not**

Cross-referencing `media`'s own 142 imported `AX_*` symbols: it imports `AX_ENGINE_Deinit`
**only** — none of `AX_ENGINE_Init`, `CreateContext`, `CreateHandle`, `GetIOInfo`, or
`RunSync`. `media` owns the full `AX_VIN`/`AX_ISP`/`AX_IVPS`/`AX_VENC`/`AX_AI`/`AX_AO`/`AX_ADEC`
media-pipeline lifecycle itself (dozens of imports, §10 of `STUDY-app.md`), but the NPU engine
lifecycle is entirely internal to `libalgo.so`; `media`'s single `AX_ENGINE_Deinit` import is
most plausibly a defensive/shared teardown call (or vestigial from a shared header), not
evidence it manages engine state. `libalgo.so`'s `petkit_algo_init` (`0x4b3ac`) drives this:
it iterates a vector of per-stage init function pointers (one per `ALGO_BODY`/`ALGO_FACE`
/`ALGO_FEAT`/`ALGO_FOOD`/... — string constants `ALGO_FOOD`, `ALGO_IN`, `ALGO_DIFF`,
`ALGO_REF`, `ALGO_CURRS`, `ALGO_BODY`, `ALGO_FACE` sit right next to the
`CPetkitAlgoInterface`/`CPetkitAlgoBase<...>` typeinfo strings at `0x33fdec-0x33fe88`), each of
which — per the class-level evidence in §1/§3.2, every detector class independently exposes
`petkit_algo_model_init()`/`petkit_algo_model_run()` — creates its own `AX_ENGINE_CreateHandle`
handle for its own `.axmodel`. **Inference, well-supported by structure but not exhaustively
counted via disassembly**: this implies up to **8 separate engine handles** (one per
`.axmodel` file in `alg_model.txt`, including the split `classify_model_bb`+`classify_model_hd`
pair), all created inside `media`'s process by code living in `libalgo.so`.

### 6.3 Memory: `AX_SYS_MemAlloc`/`MemAllocCached`/`MemFree` (CMM) + `AX_POOL_*`

Confirmed by adjacent log-format strings in the same rodata region as the NPU I/O logging:
`"Allocate input{%d} { phy: %p, vir: %p, size: %lu Bytes }. fail "`,
`"Allocate output{%d} { phy: %p, vir: %p, size: %lu Bytes }. fail "` — NPU input/output tensors
are allocated as ad-hoc CMM buffers via `AX_SYS_MemAlloc`/`AX_SYS_MemAllocCached` (not from a
pre-sized `AX_POOL`), while `AX_POOL_GetBlock`/`GetBlockVirAddr`/`Handle2PhysAddr` are used
elsewhere (almost certainly for the IVPS crop/resize/dewarp frame buffers feeding the models,
matching `AX_IVPS_CropResizeVpp`/`CropResizeV2Vpp`/`CscTdp`/`Dewarp` in the same import list).

### 6.4 `libax_engine.so` version and multi-process implications

`fs/soc/lib/libax_engine.so` (157,488 bytes) embeds:

```
[Axera version]: libax_engine.so V3.0.0_20250707110135 Jul 07 2025 11:41:44 JK 2.10.1s
```

Its export list additionally includes `AX_ENGINE_GetVNPUInfo`, `AX_ENGINE_GetVNPUAttr`,
`AX_ENGINE_SetAffinity`, `AX_ENGINE_GetAffinity`, and newer `AX_ENGINE_CreateContextV2`/
`CreateHandleV2` entry points that `libalgo.so` does **not** import (it uses only the plain,
non-`V2` calls). **Inference**: the presence of VNPU/affinity APIs in this SDK build indicates
the AX620E NPU driver supports partitioned/multi-tenant access by design (used elsewhere on
Axera SoCs for concurrent multi-process AI workloads); this makes it *plausible* that a second,
independent process calling `AX_ENGINE_Init` from its own process context can coexist with
`media`'s existing handles, but this was **not verified live** (out of scope — no device
contact) and should be the first thing checked in a follow-up live/read-only session (e.g.
watch for an `AX_ENGINE_Init` failure/refusal if attempted from a second process) before
committing to that design.

## 7. Recommended integration points

**(a) Gallery matching with the stock embedding — do not attempt to call into `libalgo.so`'s
C++ internals.** The 512-d `feat_model` embedding exists in-process as a `std::vector<float>`
(§3.2) but is not reachable through any documented/dlsym'd entry point, and the private
`CPetkitAlgoPetfeat`/`BoxInfo`/`FaceCropBBoxInfo` object layouts would have to be reverse
engineered and kept in lock-step with every firmware update — too fragile for a maintained
integration. **Recommended path**: run `petkit_face_rec_mtl_s2_v5_sim.axmodel` **independently**,
in the first-party agent's own process, via a fresh `AX_ENGINE_Init`/`CreateHandle` (same model
file, same 512-d output, verified ground truth from §3.1) against a face crop obtained by the
agent's own body/face detection (reusing `petkit_pet_1class_2026_04_15.axmodel` +
`petkit_cat_dog_mv2_035_kps_porb_roi_v8_224x224.axmodel`, or a much smaller custom model if the
budget in `STUDY.md` — ≤5 MB RSS — makes even those too heavy). Build and own a gallery/matcher
independently of `/opt/feature.bin` (own file, own format, e.g. two named vectors + a running
cosine-similarity threshold — the stock `petkit_petfeat_cos_distance` was fully disassembled and
is a plain runtime-dimensioned L2-normalize + dot-product, trivial to reimplement).

**(b) Running a custom classifier on the crop.** Since libalgo's own crop/bbox output is not
externally observable either (§5), the agent must independently detect+crop from the frame
ring already planned in `STUDY.md` ("attach as an extra reader to media's existing H.264
ring") — it cannot piggyback on libalgo's `/tmp/saveFace.jpg` reliably (written only on
libalgo's own enrollment/match cadence, not guaranteed to exist for every visit, and racy to
poll from a second process). A lightweight custom classifier (even a small linear/MLP head
over a much smaller backbone, or reusing the stock 512-d embedding + a from-scratch two-cat
cosine/kNN gallery as in (a)) run once per detected visit satisfies the "<=5MB RSS, event-driven,
~0% idle CPU" constraint far better than trying to intercept libalgo's own pipeline.

**Both paths converge on the same conclusion**: the agent should be a **second, independent
NPU client process** running the stock `feat_model` (or a purpose-built lighter model) on its
own captured crops, rather than trying to read results out of `libalgo.so`/`media`. The public
`petkit_get_event_result_info` event stream (pet_id/score/action_type/exception_type/timing)
remains useful as a **trigger signal** ("a pet-visit event just happened") even though it
carries no reusable identity payload — the agent can listen for it (or independently for the
same body-detector trigger) to know *when* to run its own inference, satisfying the
event-driven requirement without polling.

## 8. Open questions

1. **Exact `petkit_event_result_info` struct layout** (byte offsets/`sizeof`). Field order and
   C types are solid (§4, from a printf format string); offsets were not recoverable from
   static disassembly of `media`'s `petkit_event_result_callback` in the time available (Thumb
   decode desynced from the function's `.symtab` entry point — needs either a smarter
   alignment search or a single live read of the struct).
2. **`/opt/feature.bin` binary format** (header layout, CRC32 placement, per-entry record
   size). Confirmed to exist and be versioned (`"v0.0.3"`) and CRC-checked; not present in any
   offline image (populated at runtime under `/opt`), so its byte layout could not be dumped
   and parsed offline. A read-only `cat /opt/feature.bin` on a future live/read-only session
   would resolve this completely, now that the exact filename and owning function
   (`petkit_extract_feature_from_file`) are known.
3. **`feat_model` (face-rec) input crop resolution.** Not found in the `.axmodel` metadata
   window inspected (`inputs_info` was absent where `outputs_info` was present); do not assume
   a value — would need either a deeper container-format parse or a live probe via
   `AX_ENGINE_GetIOInfo`.
4. **Exact handle count for `AX_ENGINE_CreateHandle`** — inferred at up to 8 (one per
   `.axmodel` file) from the modular per-class `petkit_algo_model_init/run` pattern, not
   confirmed by counting call sites (ARM PLT stub sizes in this binary are not uniform,
   12 vs 16 bytes, which broke straightforward call-site-counting via PLT-index arithmetic).
5. **Multi-process NPU coexistence** — `libax_engine.so` V3.0.0 exposes VNPU/affinity APIs
   suggesting driver-level support for concurrent processes, but this is inference from symbol
   presence only; not verified against the live device (out of scope for this offline task).
6. **`/opt/upload_face_jpg %d %d %d` argument semantics** — inferred as
   `(pet_id, face_feature_id, score-or-event-id)` from adjacent debug-string context; the
   script itself was not located/extracted for direct confirmation.
7. **`prob` output of `feat_model`** (the second, scalar tensor alongside the 512-d `feat`
   vector) — presumed to be a face-quality/liveness gate compared against `featThresh`, not
   confirmed by tracing its consumer.
